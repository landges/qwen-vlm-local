# Qwen VLM Local: заметки по production-развёртыванию

Этот репозиторий содержит локальный OpenAI-совместимый сервер Qwen на базе
`llama.cpp` и GGUF-модели. Документ фиксирует текущую конфигурацию,
рекомендованный профиль тестирования и варианты дальнейшего масштабирования.

## Текущие вводные

- GPU на production: NVIDIA A100, доступно 40 ГБ VRAM.
- Текущая модель: `Qwen3.5-35B-A3B-UD-Q6_K_XL.gguf`.
- Движок: `llama-server` из CUDA-образа `llama.cpp`.
- Максимальный рабочий контекст: около 140 000 токенов.
- Нагрузка: до 10 000 запросов в сутки.
- Большинство запросов выполняется без reasoning.
- При текущей нагрузке остаётся около 5 ГБ VRAM.
- На узле доступно около 8 ГБ системной RAM, процесс использует примерно 3 ГБ.

`A3B` означает, что на каждом токене активируется около 3 млрд параметров.
Однако все 35 млрд параметров MoE-модели всё равно должны храниться в памяти.

## Что важно понимать

### Open WebUI не заменяет inference engine

Open WebUI является пользовательским интерфейсом. Модель всё равно должен
запускать `llama.cpp`, vLLM, SGLang, Ollama или другой inference engine.

Типовая схема:

```text
Пользователь
    |
Open WebUI (опционально)
    |
Gateway / очередь / rate limit
    |
llama-server
    |
Qwen GGUF на A100
```

### Свободная VRAM не гарантирует высокую пропускную способность

Даже если модель и cache помещаются в VRAM, узким местом могут оставаться:

- обработка длинного prompt (prefill);
- один доступный inference slot;
- очередь одновременных запросов;
- повторная обработка контекста;
- пропускная способность памяти GPU;
- ошибки восстановления состояния гибридной DeltaNet-архитектуры.

### Системная RAM

Если все слои и KV/cache размещены на GPU, 8 ГБ RAM могут быть достаточны для
одного `llama-server`. Для production разумнее иметь 16 ГБ, но увеличение до
64–96 ГБ само по себе inference не ускорит.

При 8 ГБ RAM не следует включать:

```text
--mlock
--no-mmap
```

Они могут потребовать загрузить значительную часть GGUF в физическую RAM.

## Рекомендованный профиль теста

Первый тест нужно провести на текущей Qwen3.5 Q6. Не следует одновременно
менять модель, движок и квантизацию: иначе невозможно определить причину
изменения качества или производительности.

Рекомендуемая команда:

```bash
exec /app/llama-server \
  --model "${MODEL_PATH}" \
  --mmproj "${MMPROJ_PATH}" \
  --host 0.0.0.0 \
  --port 8000 \
  --ctx-size 147456 \
  --parallel 1 \
  --threads 16 \
  --batch-size 2048 \
  --ubatch-size 512 \
  --n-gpu-layers 999 \
  --flash-attn on \
  --cache-type-k q8_0 \
  --cache-type-v q8_0 \
  --cont-batching \
  --chat-template-kwargs '{"enable_thinking":false}' \
  --metrics
```

Если текущая сборка поддерживает параметр `--reasoning-budget`, можно также
добавить:

```bash
--reasoning-budget 0
```

Проверка поддержки:

```bash
/app/llama-server --help | grep reasoning
```

### Почему выбраны эти параметры

| Параметр | Значение | Причина |
|---|---:|---|
| `ctx-size` | `147456` | 140k входа и небольшой резерв для ответа |
| `parallel` | `1` | безопасный профиль для гибридной DeltaNet-модели |
| `batch-size` | `2048` | ускорение длинного prefill |
| `ubatch-size` | `512` | ограничение пикового расхода VRAM |
| `flash-attn` | `on` | снижение стоимости длинного контекста |
| `cache-type-k/v` | `q8_0` | экономия cache относительно FP16 |
| `enable_thinking` | `false` | основной production-сценарий |

Если возникает CUDA OOM, сначала уменьшить:

```bash
--batch-size 1024
```

Если этого недостаточно:

```bash
--ubatch-size 256
```

Контекст следует уменьшать только после проверки этих двух параметров.

## Что проверить в startup-логе

```bash
docker logs qwen-vlm 2>&1 | grep -Ei \
  "offload|buffer size|KV|recurrent|CUDA_Host|CUDA0|CPU_Mapped|n_ctx|n_seq"
```

Желательный результат:

```text
offloaded 41/41 layers to GPU
CUDA0 model buffer size = ...
CUDA0 KV buffer size = ...
```

Интерпретация:

- `CUDA0 model buffer` — веса находятся в VRAM;
- `CUDA0 KV buffer` — KV/cache находится в VRAM;
- `CPU KV buffer` — часть cache находится в системной RAM;
- `CPU_Mapped model buffer` — используется RAM/mmap;
- `CUDA_Host compute buffer` — pinned host RAM для обмена с GPU;
- неполный `offloaded N/41` — часть слоёв выполняется на CPU.

## Диагностика дисковой активности

GGUF по умолчанию загружается через `mmap`. Высокое чтение диска при запуске
контейнера и первом прогреве нормально. Постоянное чтение на каждом запросе
может указывать на swap, перезапуск worker, вытеснение page cache или запись
контекстных состояний.

Мониторинг:

```bash
free -h
swapon --show
vmstat 1
iostat -xz 1
docker stats qwen-vlm
```

В `vmstat`:

- `si` — чтение из swap;
- `so` — запись в swap;
- `wa` — ожидание диска.

Определить I/O процесса:

```bash
pidstat -d -p "$(pgrep -n llama-server)" 1
sudo iotop -oPa
```

Проверить перезапуски:

```bash
docker inspect qwen-vlm --format '{{.RestartCount}}'
docker logs --since 1h qwen-vlm
```

Если после загрузки модели `si/so` равны нулю, а I/O `llama-server` почти
нулевой, диск нагружает другой процесс или подсистема Docker.

## План нагрузочного теста

До начала теста сохранить версии:

```bash
/app/llama-server --version
nvidia-smi
free -h
swapon --show
```

Проверить четыре профиля:

| Профиль | Размер входа | Параллельность |
|---|---:|---:|
| Короткий | 2–4k | 1 |
| Средний | 32k | 1 |
| Длинный | 100k | 1 |
| Максимальный | 140k | 1 |

Для каждого запуска записать:

- TTFT (время до первого токена);
- prompt tokens/s;
- generation tokens/s;
- пиковую VRAM;
- используемую RAM;
- disk read/write;
- GPU utilization;
- результат и стабильность streaming.

После одиночных тестов одновременно отправить 5–10 запросов. Один запрос
должен обрабатываться, остальные — ожидать во внешней ограниченной очереди.
При переполнении gateway должен возвращать `429` или `503`, а не принимать
неограниченное число длинных запросов.

## Что не включать в первом тесте

- `--parallel 2` и выше;
- Qwen3.6 вместо текущей модели;
- MTP/speculative decoding;
- `--mlock`;
- `--no-mmap`;
- сохранение slot cache на диск;
- reasoning;
- несколько реплик на одной 40-гигабайтной GPU.

## Квантизации

Ориентировочное сравнение для модели 35B-A3B:

| Формат | Размер | Особенности |
|---|---:|---|
| GGUF Q6_K_XL | 30–32 ГБ | лучшее качество, меньше свободной VRAM |
| GGUF Q5_K_XL | около 27 ГБ | хороший баланс качества и памяти |
| GGUF Q4_K_XL | около 22 ГБ | больше памяти под cache |
| GPTQ/AWQ INT4 | 18–22 ГБ | предназначен для vLLM, лучше batching |

Для текущего `llama.cpp` подходящим тестовым обновлением является:

```text
unsloth/Qwen3.6-35B-A3B-GGUF
Qwen3.6-35B-A3B-UD-Q5_K_XL.gguf
```

Однако Qwen3.6 нужно тестировать отдельно: свежая реализация гибридной
архитектуры в `llama.cpp` имеет зарегистрированные проблемы с multi-turn
контекстом и восстановлением slot state.

## Дальнейший путь масштабирования

Если текущая Q6-модель проходит SLA, рекомендуется оставить:

```text
Gateway с ограниченной очередью
    -> llama-server, parallel=1
    -> Qwen3.5-35B-A3B Q6 GGUF
```

Если одного слота недостаточно, следующий технический эксперимент:

```text
Gateway
    -> vLLM
    -> Qwen/Qwen3.5-35B-A3B-GPTQ-Int4
```

GGUF в vLLM остаётся менее зрелым и не является рекомендуемым production-путём.
Для vLLM лучше использовать Safetensors GPTQ/AWQ checkpoint.

Open WebUI можно добавить в любую схему как интерфейс, но он не увеличивает
производительность inference.

## Итоговый baseline

Для ближайшего теста:

```text
Модель:       Qwen3.5-35B-A3B Q6_K_XL
Контекст:     147456
Слоты:        1
Thinking:     выключен
FlashAttention: включён
KV/cache:     Q8_0
Batch:        2048
Micro-batch:  512
RAM:          текущие 8 ГБ, без mlock/no-mmap
```

Этот профиль должен использоваться как контрольная точка перед сравнением с
Q5, Qwen3.6 или vLLM.
